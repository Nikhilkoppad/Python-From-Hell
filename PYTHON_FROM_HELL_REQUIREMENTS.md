# PYTHON FROM HELL

## MASTER PRODUCT REQUIREMENTS

### Version 1.0 — The Fucking Blueprint

---

# 1. THE CORE IDEA

Python From Hell is not supposed to be a normal coding course.

It is an **adaptive Python training platform disguised as a brutal, hilarious hell-themed coding experience.**

The learner should feel like:

> "I voluntarily walked into hell, and now this bastard is going to teach me Python whether I like it or not."

The platform must combine:

* Real Python education
* Real Python execution
* Adaptive learning
* Practical coding
* Brutal humor
* Profanity
* Memorable explanations
* Immediate feedback
* Progress tracking
* Mastery-based progression
* Real-world coding preparation
* Interview preparation

The goal is NOT simply:

> "Complete 50 lessons."

The goal is:

> **Actually make the learner capable of writing Python without panicking every time they see an error message.**

---

# 2. PERSONALITY — THIS IS CRITICAL

The entire product personality should be:

* Brutal
* Funny
* Profane
* Sarcastic
* High-energy
* Memorable
* Encouraging underneath the brutality
* Never boring
* Never corporate
* Never generic

The platform should use Hinglish/Hindi-style profanity naturally where appropriate.

Examples of tone:

> "BC, you just deleted the variable and then asked Python where the variable went."

> "Kya gand phaad code likha hai. It actually works."

> "Python ne error diya hai. Python tera dushman nahi hai. Tu bas usko galat instruction de raha hai, BC."

> "Congratulations, you fucked up. Excellent. Now let's understand WHY."

> "SyntaxError dekh ke bhaagna nahi hai. Error message tera enemy nahi, tera free debugger hai."

> "Aaj `if` samajh le. Kal nested conditions dekh ke apni zindagi ke decisions pe shaq karega."

The profanity must serve a purpose:

**HUMOR + MEMORY + MOTIVATION + TEACHING.**

Do NOT insert random profanity into every sentence just because profanity was requested.

The experience should feel intentionally written, not like a bot repeatedly saying "fuck" every three words.

However, profanity should be a **persistent part of the product identity**, especially in:

* HellGate
* lesson introductions
* failure messages
* successful challenge reactions
* debugging feedback
* boss fights
* achievements
* error explanations
* motivational messages

The system should have multiple roast variations so the same insult is not repeated constantly.

```python

```

> "Congratulations. You just told Python to remember that `age` is 25."

> "Do not overthink this shit."

```text

```

# 11. REAL PYTHON EXECUTION

THIS IS NON-NEGOTIABLE.

The current regex-based print simulation must eventually be removed.

The application must execute actual Python.

Prefer a browser-based runtime such as Pyodide if compatible with the project.

Execution should support:

* stdout
* stderr
* syntax errors
* runtime errors
* tracebacks
* timeouts
* cancellation
* execution isolation
* deterministic evaluation

Prefer executing Python inside a Web Worker where appropriate so an infinite loop cannot freeze the UI.

Example:

```python
while True:
    pass
```

The application must NOT freeze because a learner wrote this.

There must be execution limits.

---

# 12. CODE EVALUATION

Do not judge challenges only by comparing one printed string.

A challenge should define its requirements.

For example:

> Create a function called `square` that returns the square of a number.

The system should test:

```python
square(2) == 4
square(5) == 25
square(-3) == 9
```

Potential challenge metadata:

* Expected behavior
* Function name
* Parameters
* Return type
* Required concepts
* Hidden tests
* Edge cases
* Difficulty
* Topic
* Common mistakes
* Hint strategy

The learner should not pass simply by hardcoding:

```python
return 4
```

if the challenge requires:

```python
square(2)
```

to work correctly.

# 13. JUDGMENT SYSTEM

After execution, determine:

### PASS

The code satisfies the requirements.

Respond with celebration + roast.

Example:

> "HOLY SHIT."

> "It actually works."

> "I was fully prepared to insult this code."

> "+50 XP"

### FAIL

Explain:

1. What happened
2. Why it happened
3. What concept was misunderstood
4. What the learner should try next

Then roast the mistake.

Example:

> "BC, your loop isn't looping."

> "You told it to stop before it even started."

Then explain the actual programming mistake.

# 43. ROAST & GAALI ENGINE — CORE PRODUCT FEATURE

The roasting system is NOT decoration.

It is one of the defining features of Python From Hell.

The platform should have a dedicated Roast Engine capable of producing highly varied, context-aware, funny, savage Indian/Hinglish-style roasting.

NEVER repeatedly show the same roast when many alternatives are available.

Possible styles:

* "BC, Python ne spelling mistake pakad li."

* "BC, code technically chal raha hai, bas dimaag nahi."
* "Gandu, logic ne resignation de diya."
* "Tera code answer de raha hai, bas sahi answer dene se uski dushmani hai."
* "Ye solution nahi, programming ka plot twist hai."
* "Bhai, algorithm ko tune itna ghuma diya ki woh khud bhatak gaya."

### INFINITE LOOP

* "BC, loop khatam hone ka naam hi nahi le raha."
* "Gandu, Python ko treadmill pe chadha diya kya?"
* "Ye loop hai ya reincarnation?"
* "Bhai, is loop se bahar nikalne ke liye Python ko rescue team bulani padegi."
* "Loop chal raha hai. Zindagi ruk gayi hai."

### VARIABLE MISTAKE

* "BC, variable banaya tha ya naam ka confusion create kiya tha?"
* "Gandu, Python ko bata toh sahi tu kis variable ki baat kar raha hai."
* "Variable ka naam kuch aur, use kuch aur. Wah bhai."
* "Tera variable bhi soch raha hai main hoon kaun."

### INDENTATION

* "BC, indentation ko itna ignore kyun kar raha hai?"
* "Python whitespace ko seriously leta hai. Tu nahi."
* "Gandu, spaces se itni dushmani kis baat ki?"

### WRONG ANSWER

* "Bhadwe, output technically output hai. Sahi output nahi hai."
* "BC, target 42 tha aur tu 17 leke aa gaya. Confidence dekho."
* "Answer galat hai, lekin attitude Olympic level ka hai."
* "Python ne tera answer dekha aur quietly bola: nahi bhai."

### SUCCESS

Success should ALSO be varied.

Do NOT always say:

> "Good job!"

Instead:

* "HOLY BC. It fucking works."
* "Aaj toh gand phaad di."
* "MC, finally code ne cooperate kiya."
* "Kya baat hai. Aaj Python ne tujhe nahi, tune Python ko maara."
* "BSDK, ye actually correct hai."
* "Land fakir se coder banne ki journey officially shuru."
* "Aaj bach gaya, gandu. Next challenge mein milte hain."
* "Unexpected development: tera code kaam kar raha hai."
* "BC, mujhe insult karne ka mauka hi nahi diya."

# 47. ROAST VARIATION

Track recent roast messages.

Do not repeat the same message immediately.

Avoid:

```text
Attempt 1 ? "BC, gand mara."
Attempt 2 ? "BC, gand mara."
Attempt 3 ? "BC, gand mara."
Attempt 4 ? "BC, gand mara."
```

Instead:

```text
Attempt 1 ? syntax roast
Attempt 2 ? sarcastic roast
Attempt 3 ? metaphor roast
Attempt 4 ? Indian/Hinglish roast
Attempt 5 ? absurd comedy roast
Attempt 6 ? motivational roast
```

Maintain a recent-roast history.

Prefer messages that have not been used recently.

# 48. CONTEXT-AWARE ROASTING

Roasting should depend on what happened.

Inputs may include:

* Error type
* Topic
* Challenge
* Attempt number
* Number of previous failures
* Whether hints were used
* Whether the learner fixed a previous mistake
* Difficulty
* Time/effort where appropriate
* Success/failure
* Roast intensity
* Recent roast history

Example:

### First failure

Light savage:

> "Not terrible. Just wrong enough to be interesting."

### Third failure

Escalate:

> "BC, we've now visited the same bug three times. At this point you're not debugging it, you're dating it."

### Finally succeeds

De-escalate into celebration:

> "HOLY SHIT. After all that bakchodi, you fixed it."

# 55. FUTURE AI ROASTING

Eventually an AI can generate new roast variations.

However:

AI-generated roasts should be filtered against safety and product rules.

The deterministic Roast Engine should remain available as a fallback.

Never make the application dependent on an external AI API just to display a failure message.

If AI generation fails:

```text
Use local roast library.
```

The learner should never see:

> "Roast generation failed."

Instead:

> "BC, even the roast engine took one look at your code and needed a break."

# 56. THE GOLDEN ROAST RULE

Every roast should ideally accomplish at least TWO of these:

* Make the learner laugh
* Identify the mistake
* Explain the concept
* Motivate another attempt
* Reinforce memory
* Celebrate progress

If a roast only insults the learner and teaches nothing, it is a weak roast.

If it teaches without personality, it is boring.

Python From Hell needs both.
